# Release 0.9.4 (2026-11-21)

Previous release: 0.9.3. A patch release of the demo data tools. The application, the policy
(HL-LAP-POLICY-2026.14) and the models are unchanged.

## Highlights

- **Every kind of case the area manager can face, generated rather than hand-tuned.**
  `scripts/demo_catalogue.py` asks the engine itself: it prices several hundred applicant
  profiles on a throwaway copy of the store and keeps one for each combination of grade,
  tenure band, where the ask sits against the floor, and the competitor evidence. The
  result is 92 cases to decide plus 9 already decided (one or more of each outcome), all
  between 13% and 17%. The coverage page `docs/demo/area_manager_cases.md` shows every
  combination and, where there is no case, why.
- **Impossible and not found are kept apart.** 20 combinations are impossible under the
  policy (an A+ loan of up to five years has a card rate of 13.00%, which is also its floor,
  so no ask can exist). 78 were not found: mostly because the engine always recommends the
  floor for grade C and for grade B over seven years, so no ask can sit at or above the
  floor there; the rest had room, but no probed file produced that exact mix.
- **Probe where the cases will be used.** Cases are found against one set of models. The
  AWS server trained its own, so its catalogue is probed on the server.

## Changes

### Added
- `scripts/demo_catalogue.py`: every area-manager case the policy and the engine allow,
  found by probing the engine rather than tuned by hand. `probe` prices several hundred
  applicant profiles on a throwaway copy of the store (it refuses the live port) and picks one
  per cell of grade (A+ to C) x tenure band x ask position (within room, at the floor, below it)
  x competitor evidence (five kinds); `create` posts them to a server and checks each lands in
  its cell, labelling it by what it observes if not; `report` writes the coverage page
  `docs/demo/area_manager_cases.md`. The catalogue holds 92 cases for the area manager to
  decide (82 cells and 10 special situations: new to credit, a score near 675, LTV, ticket,
  FOIR and age near their limits, late EMIs, a balance-transfer threat, a month-end target
  with no evidence, a customer not bargaining on price) and, with `--decide-history`, 9 cases
  the area manager has already decided: approve as asked, approve at the floor, counter,
  decline and uplift. Every rate is checked against the 13-17% band before it is sent.
- Every cell without a case says why: 20 are impossible under the policy (for example A+ up
  to 60 months, whose card rate is already the 13% floor); 78 were not found by the probe,
  most because the engine always recommends the floor for grade C and for B over 84 months.
- `scripts/scratch_api.py`: start and stop a throwaway API over a copy of the store, for
  probing on any machine, including the AWS server (whose models differ from a laptop's).

## Upgrade steps

Nothing to deploy: the running application is unchanged.

- Same models as the catalogue (this laptop): `python scripts/demo_catalogue.py create
  --base http://127.0.0.1:8000 --decide-history`.
- Other models (the AWS server): start a throwaway API with `scripts/scratch_api.py start`,
  `probe --scratch --out <file>` against it, stop it, then `create --catalogue <file>`. The
  coverage page's "How to run" section has the exact commands.
- Run `create` once per server: a second run adds a second set.

## Known issues

- No case sits near break-even: the smallest gap between a floor and the break-even rate in
  the probe was 3.28 points, so no permitted ask comes close.
- The probe's run time is not recorded in this catalogue (the system clock jumped during
  the run).
- Everything listed under Known issues in 0.9.3 still stands.
