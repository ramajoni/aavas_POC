# Lending policy kit

A common structure for a lending pricing policy. Any lender can fill it in with its own values, check it, and drop it into the pricing engine.

This README is for two readers. The risk or credit-policy team fills in the policy. The engineer installs it and keeps the kit working.

## What the kit is

The kit is a blank policy that follows the same structure as a policy the engine already runs. It was generated from that live policy. It has four parts.

| File | What it is |
| --- | --- |
| `sections.yaml` | The single source of section metadata: title, purpose, requirement, owner, who reads it. |
| `lending_policy.schema.json` | A JSON Schema (draft 2020-12) of the structure. It checks types, ranges and required keys. |
| `lending_policy.template.yaml` | A blank policy. Each section has a comment header and typed placeholders. |
| `README.md` | This guide. |

The kit stays in step with the live policy. The command `python scripts/policy_kit.py build` regenerates the schema, the template and the table below.

Three ideas matter most.

- The structure is common. The names inside some sections are not. Grade labels, segments, property types, scorecard measures and reason codes are the company's own. The schema accepts any name there.
- The engine reads only some of the file. Those sections are `required`. The rest document policy and are checked for shape only.
- The schema checks one value at a time. The engine's own checks look across values, for example that the matrix agrees with the grade rates. A file must pass both.

## Required, optional and jurisdiction

Every section has one of three requirements.

- **required.** The engine reads the section. The file fails the schema if it is missing. Inside a required section, the keys the engine indexes directly are required too. Other keys are optional.
- **optional.** The engine does not read it, or reads it with a default. Keep it if the company uses it. If you keep it, it must still have the right shape.
- **jurisdiction.** The section is tied to one country or regulator. Replace it with the local equivalent, or leave it out. See the last section of this guide.

Some sections have **own key names**. In these, the keys are the company's own names. The template shows two examples. Replace them with real names and add as many as needed. The schema accepts any key there.

Extra keys and extra sections are allowed. The schema does not check them.

## How to adopt

1. **Copy the template.** Copy `lending_policy.template.yaml` to the place where the company keeps its policy, for example `config/pricing_policy.yaml`. Keep the original untouched.
2. **Fill it in.** Work part by part. The owner named in each section header is the team that should supply the values.
   - Replace every `"<...>"` placeholder.
   - Replace the example key names with the company's own names.
   - Rates are annual percentages. Write `13.00` for 13% p.a. Spreads are in basis points.
   - Fractions such as FOIR and LTV are between 0 and 1. Write `0.55`, not `55`.
   - Tenure is in months. Months must be positive whole numbers.
   - A grade that gets no offer has `null` for its rate and loading.
3. **Validate.**

   ```
   python scripts/policy_kit.py validate path/to/policy.yaml --cutoffs config/model_config.yaml
   ```

   The command does three things.
   - It checks the file against the schema. Each error shows the YAML path, what was expected and what was found. A placeholder you forgot is reported as "not filled in".
   - It runs the engine's own checks on the file (see the invariants below). The risk model's grade cutoffs come from `risk.grade_cutoffs` in the model config.
   - It prints a summary and exits non-zero if anything failed.
4. **Add sample cases.** Write a few worked applications that show the policy giving the answers the team expects. Include a normal approval, a discount at each approval level, a declined grade and a hard-limit breach. Keep them with the tests so a later edit that changes an answer is caught.
5. **Version it.** Give the file a new `policy_version`, fill in `supersedes`, set `effective_from`, and record what was decided in `decisions`. Keep the old file. See the versioning section.

## Policy invariants

The engine checks that the policy agrees with itself. The readable copy of these rules is the `invariants` section of the policy. The checks themselves are in `src/<package>/governance/policy_checks.py`.

| Id | The rule |
| --- | --- |
| INV-01 | In each model, the weights of a category's measures add up to the category weight. The category weights add up to 100. |
| INV-02 | Each matrix rate equals the grade's base rate plus the tenure adjustment for that column. A grade with no base rate has no matrix rate. |
| INV-03 | The card rate floor plus the grade loading (bps divided by 100) equals the grade's base rate. A grade with no loading has no base rate. |
| INV-04 | Each tenure loading equals the matching tenure adjustment, on the same month boundaries. |
| INV-05 | Every matrix rate lies inside the pricing band. The pricing band equals the card rate floor and ceiling. |
| INV-06 | Sub-score factor weights add up to 100 for employer, industry and builder. |
| INV-07 | Every band list ends with an `else` catch-all. `ge` bands go down. `le` bands go up. |
| INV-08 | Every action or outcome word used in the file appears in the action catalogue. |
| INV-09 | Every grade the risk model can produce has a risk grade loading entry. |
| INV-10 | No approval level may approve a premium. The matrix rate is the ceiling. |
| INV-11 | Maximum tenure in years times 12 equals maximum tenure in months. It also equals the last tenure band's upper month. |
| Reason codes | Every scored measure that can trigger an action has a reason code. This check is skipped if the file has no `reason_codes` section. |

Two of these checks are skipped when the optional section is absent: INV-08 needs `actions`, and the reason-code check needs `reason_codes`. A company that wants these controls should keep both sections.

INV-10 is a house rule. It says the matrix is the most any offer may carry. A lender that allows approved premiums would have to change the engine check as well as its policy.

## Versioning

Every decision records the `policy_version` it was priced under. That is how a reviewer can read the exact policy behind an old decision.

- **Naming.** Pick one scheme and keep it, for example `XX-POLICY-2026.14`. The number after the prefix is compared as numbers, so `2026.9` sorts before `2026.10`. The prefix only breaks a tie. A new file must sort after the one it replaces.
- **supersedes.** Put the version this file replaces. Leave it `null` for a first policy.
- **effective_from.** The date the policy starts, as `YYYY-MM-DD`. Set it on approval.
- **status.** Say where the policy stands, for example draft pending approval, or approved.
- **decisions.** A numbered log (`D-01`, `D-02`, ...). One line per decision on an open item, with the reason. It is the audit trail for why a value is what it is.
- **Archive.** Keep each earlier version as written, one file per version, named after its `policy_version`. The engine reads the live file and the archive, and also the change history when a policy is replaced through the configuration screen.
- **Decisions log in the store.** Each priced decision stores its `policy_version`. The regulatory report counts how many decisions carry one.

Never edit an approved file in place. Make a new version.

## Keeping the kit in step

For the engineer. The kit is generated, not hand-kept.

- Change `config/pricing_policy.yaml` or `policy_kit/sections.yaml`, then run `python scripts/policy_kit.py build`.
- `build` stops if a section is in the policy but not in `sections.yaml`, or the other way round. Add the new section's metadata first.
- The hand constraints (rate ranges, integer bps, fractions, positive months) are set by key name in `scripts/policy_kit.py`. A key called `*_bps` is an integer. A key with `foir` or `ltv` in its name is a fraction. A key with `months` in its name is a positive integer.
- When the engine starts reading a new key with direct indexing, add it to `engine_read_keys` for that section. It then becomes required in the schema.
- The test `tests/test_policy_kit.py` fails if the committed schema, template or table differ from what `build` produces.

## Parts that are specific to India and RBI

The pricing engine and the structure are general. Some content is tied to Indian regulation. A lender elsewhere should replace or drop it.

**Sections marked `jurisdiction`**

- `housing_regulatory_ltv`. The loan-to-value ceilings the housing finance regulator sets by loan amount, for housing loans only.
- `effective_ltv`. The rule that takes the lowest of the grade, regulatory slab and collateral ceilings. The regulatory slab is the Indian one.
- `affordability`. The FOIR rule for salaried borrowers and the DSCR rule for business borrowers. FOIR and DSCR are the Indian norms for repayment capacity.

**Content inside other sections**

- `constraints`. The maximum LTV, FOIR and loan amount should respect the local regulator's limits.
- `fair_pricing`. The key fact statement duty (`kfs_required`) follows RBI fair-practice rules on disclosure.
- `mandatory_rules`. Credit bureau minimum, KYC, sanctions and politically exposed person handling follow Indian norms. Other markets have their own bureaus and screening lists.
- `scorecard`. Measures such as GST filing, GST and banking variance, and income-tax return reconciliation exist because of Indian tax filings. The measure names are the company's own. Replace them with local evidence.
- `guardrails` and `controls`. Evidence freshness, screening and separation of duties should follow the lender's own regulator.

Everything else, such as the pricing matrix, the optimiser, the approval levels, the override rules and the decision record, is not tied to a country.
